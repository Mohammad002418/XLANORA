# Financial Management: Implementation Plan (Phase 1)

Status: Phase 1 implemented in the local version (SQLite) and as a Supabase migration (schema and row-level security only). Real payments are NOT active.

## 1. Analysis of the existing project (before changes)
- **Frontend:** static HTML generated by `build/build.py` (EN and AR), plain JavaScript (`site/assets/js`), no framework.
- **Backend (local):** Python standard-library HTTP server (`server/app.py`), SQLite (`server/schema.sql`).
- **Backend (Supabase):** Auth, PostgreSQL with row-level security (`supabase/migrations/001` to `006`).
- **Roles:** `client` and `freelancer`. No administrator role exists.
- **Bookings:** pending, accepted, rejected, cancelled, completed. Price comes from the service on the server (`services.price_sar`, whole riyals).
- **Payments:** none. There is no payment code, no money tables, and no refund or payout logic.
- **Deployment:** Netlify publishes `site/` after `build/build.py`. Security headers in `site/_headers`. Supabase migrations are run by hand in the SQL editor.
- **Leftover:** a Next.js scaffold (`app/`, `components/`, `package.json`) that the site does not use.

## 2. Money rules
- All amounts are integers in halalas (1 SAR = 100 halalas). No floating-point money anywhere.
- Commission rate is stored in basis points (1000 = 10%), changeable by an administrator between 0% and 50%. Each transaction stores the rate it was charged at, so later changes do not rewrite history.
- Commission = floor(amount x rate / 10000). Net = amount - commission. Gross = commission + net, enforced by a constraint.

## 3. Lifecycle
1. Client requests a booking (pending). Freelancer accepts.
2. Client starts payment for an accepted booking. A payment transaction is created (pending). A second open payment for the same booking is refused by a unique index.
3. The payment provider confirms the payment with a **signed webhook**. The server verifies the signature and the timestamp, records the event id (duplicates are ignored), checks the amount, then moves the transaction pending to paid. Commission and freelancer earning are created once (unique on transaction).
4. Booking completed (after it ends) moves the earning to `awaiting_confirmation`.
5. Provider confirms payout eligibility (signed webhook `earning.eligible`) moves it to `available`. Only then does the freelancer see it as available.
6. Freelancer requests a payout from available earnings. Administrator marks it paid (or rejects it, releasing the earnings).
7. Client cancels a paid booking: a refund request is created. Administrator approves it: the provider refunds, the transaction becomes refunded, commission and earning are reversed. Refunds cannot exceed the amount paid, and cannot reverse an earning that was already paid out.

## 4. Payment providers
- A provider interface (`server/finance.py`): start payment, fetch status, refund, verify webhook.
- Only a **sandbox** provider is implemented. Its webhooks are signed with `XLANORA_SANDBOX_WEBHOOK_SECRET`. Without that variable, webhooks are refused.
- No card data is ever stored. No provider secret is written to the repository or the frontend.
- Real providers (for example PayPal) are not implemented. They need an approved account, legal arrangements and explicit authorization.

## 5. Tables
payouts, sandbox_payments, subscription_plans, user_subscriptions, payment_transactions, platform_commissions, freelancer_earnings, refunds, payment_webhook_events, financial_audit_logs, platform_settings. Users get an `is_admin` flag (set only from the command line; never at sign-up).

## 6. Permissions
- Administrator only: commission settings, financial reports, subscription plans and assignments, refund decisions, payout decisions, transaction list.
- Freelancer: only their own earnings, payouts, and subscription status.
- Client: only their own payments and refunds.
- Webhooks: no session; accepted only with a valid signature.

## 7. Not built in Phase 1
- Live payment processing; real provider integration.
- Supabase payment workflow (Edge Functions for webhooks and payout calls). The Supabase migration provides the tables, constraints and row-level security only.
- Tax invoices, VAT, multi-currency, escrow, wallets.

---

## Status (V9, implemented)

Built and tested: commission math (integer halalas, basis points, rounded down); payment, refund, earning, payout and subscription state machines; sandbox provider with HMAC-SHA256 signed, replay-protected, idempotent webhooks; admin dashboard with server-side access control; append-only audit log; SQLite and Supabase (migration 007) versions.

Verification: unit suite 289 tests (2 skipped on purpose); browser finance suite 25 of 25; Supabase finance SQL 17 checks on PostgreSQL 16 through migration 007.

Not built: a real payment provider (PayPal included; requires the owner's business account and written authorization), Supabase Edge Functions for payments and webhooks, admin two-factor login, partial refunds, admin password reset command.

See `docs/XLANORA_GUIDE.md` section 4 and `docs/SECURITY_TEST_REPORT.md`.
