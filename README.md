# XLANORA website

Bilingual (English and Arabic, with right-to-left layout) service website with accounts for clients and freelancers. Plain HTML, CSS and JavaScript, generated by a small Python script. Two database versions: local SQLite and Supabase.

Scope and decisions: `docs/PROJECT_MAP.md`. Open items: `docs/ORPHANS_AND_PENDING.md`.

## What is included

- Five page types in English and Arabic: Home, Services, Service detail (one page per service), About, Contact.
- Nine services: Photography, Home Maintenance, Education & Training, Graphic Design, Web Development, Video Editing, Digital Marketing, Translation Services, Social Media Management. Add a service in `build/content.py` and its slug in `server/app.py` (`SPECIALTIES`), the schema, and a new Supabase migration. `tests/test_consistency.py` fails if the lists disagree.
- Booking: freelancers manage services, weekly hours and bookings (accept, reject, complete); clients search, pick a free time and book, see status, and cancel. Double bookings, past times and wrong lengths are refused by the database itself, on both backends. No payment in this version.
- Account pages: Create account, Sign in, Dashboard (plus Sign out).
- Two account types:
  - **Client:** sends service requests and sees only their own.
  - **Freelancer:** chooses one specialty (one of the nine services) and sees requests for that specialty, including the client's contact details.
- Contact form with validation in the browser and on the server, plus a hidden spam trap.
- Responsive from 360 px wide. No horizontal scrolling.

## Requirements

- Python 3.11 or newer. Standard library only, nothing to install.
- For the Supabase version: a Supabase project, and PostgreSQL 16 locally if you want to run the SQL tests.

## Run locally (SQLite version)

```bash
python3 build/build.py                 # generate the pages from build/content.py
python3 server/app.py --port 8000      # serve the site, accounts and requests
```

Open http://127.0.0.1:8000/en/index.html or http://127.0.0.1:8000/ar/index.html.

The database is `server/data/xlanora.db`, created automatically. Use `--db <path>` to choose another file.

## Owner and administrator access

Admin accounts are created only from the server command line. The generated password is printed once; save it in a password manager.

```bash
python3 server/manage.py create-admin --email you@example.com --name "Your Name" --generate
python3 server/manage.py commission-show
```

Finance and the admin page need the local Python server (`python3 server/app.py`). Netlify only hosts the static site. Full guides: `docs/XLANORA_GUIDE.md`, `docs/DEPLOY.md` (GitHub, Supabase, Netlify steps), `docs/SECURITY_TEST_REPORT.md` (OWASP Top 10 results).

## Run the tests

```bash
python3 -m unittest discover -s tests -v        # 289 tests (2 skipped on purpose): server, accounts, bookings, portfolio, finance, OWASP security, site, consistency, upgrade
python3 tests/e2e_booking.py                    # browser test of the booking dashboard (34 checks; needs Playwright and Chrome)
python3 tests/e2e_site.py                       # browser test of every page, EN and AR, phone and desktop (27 checks)

```

Browser tests (Google Chrome and Playwright) are described in `docs/ORPHANS_AND_PENDING.md`. They cover every page on phone and desktop sizes.

Supabase schema tests (PostgreSQL 16, no Supabase account needed):

```bash
createdb xlanora_test
psql -v ON_ERROR_STOP=1 -d xlanora_test -f tests/supabase_rls_test.sql
psql -v ON_ERROR_STOP=1 -d xlanora_test -f tests/supabase_booking_test.sql   # run after the RLS test on a fresh database with 004 and 005 applied
```

Each check prints a PASS notice; the RLS script ends with `ALL SUPABASE RLS CHECKS PASSED`, the booking script with `ALL SUPABASE BOOKING CHECKS PASSED` (14 checks).

## Security notes

- Passwords are hashed with PBKDF2-SHA256 (310,000 iterations) and a random salt. They are never stored in plain text.
- Session cookies are HttpOnly and SameSite=Strict. Set `XLANORA_SECURE_COOKIES=1` when the site runs behind HTTPS.
- Only the hash of each session token is stored in the database.
- Sign-in and sign-up are rate limited per IP (10 attempts per 10 minutes). Contact requests are limited to 5 per 10 minutes.
- Wrong email and wrong password give the same result, and the server takes the same time for both.
- Requests are JSON only, limited to 8 KB, and reject unknown fields and control characters.

## Email notifications (optional)

Set these environment variables and each contact request is also emailed to `CONTACT_TO`:

| Variable | Example |
|---|---|
| `SMTP_HOST` | `smtp.gmail.com` |
| `SMTP_PORT` | `587` |
| `SMTP_USER` | your address |
| `SMTP_PASSWORD` | an app password (never commit it) |
| `SMTP_FROM` | the sender address |
| `CONTACT_TO` | `contactxlanora@gmail.com` |

Without these, requests are still saved in the database.

## Supabase version

1. Create a Supabase project.
2. In the SQL editor, run the migrations in order: `001_init.sql`, `002_accounts.sql`, `003_services.sql` (nine services), `004_bookings.sql` (services, weekly hours, bookings, database rules), `005_availability_rpc.sql` (atomic weekly-hours save), `006_portfolio.sql` (portfolio), `007_finance.sql` (payments, earnings, payouts, refunds, audit log). `008_parity.sql`, `009_photos.sql` and `010_profiles_public.sql` (service limit, administrator inbox, photo storage, freelancer directory and profile fields), `011_wishlist.sql` (client wishlist with row-level security), `012_reviews_alerts.sql` (reviews after completed bookings, category e-mail alerts), `013_verified_only.sql` (identity verification), `014_direct_payment_orders.sql` and `015_payment_currency.sql` (direct-payment orders, SAR/USD), and `016_video_uploads.sql` (uploads up to 50 MB, portfolio videos). Step-by-step publishing with GitHub, Supabase and Netlify: `docs/PUBLISH_GUIDE.md` (English, with Arabic below). A project that already ran earlier files only needs the newer ones. Back up first.
3. In `site/assets/js/config.js`, set `backend: "supabase"`, `supabaseUrl` and `supabaseAnonKey`. Use the **anon** key only. The service role key must never appear in the site.
4. In the Supabase dashboard, check Authentication settings. With email confirmation on (the default), a new account must confirm its email before signing in. The site shows a message for this.
5. Rebuild with `python3 build/build.py`.

Row-level security lets visitors send requests and nothing else. Clients read only their own requests. Freelancers read requests for their specialty. Nobody can edit or delete requests through the public API.

Note: in Supabase mode the session token is kept in the browser's local storage, as Supabase's standard client does. The site's Content Security Policy blocks inline scripts, which lowers the risk of token theft, but it cannot remove it. Use the local version where cookie sessions are required.

## Deploying as a static site

The site folder is `site/`. The pages work on any static host. `site/_headers` contains the security headers for hosts that read it (Netlify does). The local server adds the same headers automatically.

The local version needs `server/app.py` running somewhere, so it cannot run on a static host alone. `netlify.toml` builds the static site with `python3 build/build.py` and publishes `site/`. The Supabase version needs only the static files plus the Supabase project.
